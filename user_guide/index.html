User Guide

This guide is the complete reference for the redcedar Python SDK: every call, its arguments and what it returns, the settings, and the command line. For a first walkthrough, start with the Quick Start.

How Red Cedar Works

A Red Cedar model is a parameterized quantum circuit that learns to map your input features to an answer. The SDK sends your data and settings to a Red Cedar server; the server prepares the data, builds the circuits, runs them on a simulator or a quantum computer, and trains the parameters. Results come back to the SDK as plain Python values (dicts and lists).

The work has three steps, and the SDK groups its calls the same way:

Step Call What it does
Train training.run() Trains a model on your data.
Evaluate (optional) training.evaluate() Scores the model on the rows held back from its own training run: how good is it?
Use inference.run() Makes predictions on new rows you supply.

training holds everything about building a model and judging it; inference holds using it. Alongside these are datasets, analysis (understanding a dataset before training) and explainable (what the model relies on).

Long-running calls wait until the server has finished and then return the result. The server runs one job at a time; if it is busy, your job waits in a queue and starts when the job before it finishes.

Installation

pip install redcedar

The only dependency is requests. The example notebooks also plot with matplotlib: pip install "redcedar[plotting]".

To read the source, or to work on the SDK itself, install it from a clone of the repository instead:

git clone https://github.com/coherent-computing/redcedar.git
cd redcedar
pip install -e .

Connecting to a Server

A Server on Your Own Machine

If you have the Red Cedar engine installed, start its server from the red-cedar folder with ./run_server.sh (Linux, Mac) or run_server.bat (Windows). It listens on port 8002, and the SDK connects to http://127.0.0.1:8002 by default. The server only accepts requests with the key that the script sets (the line export BACKEND_API_KEY=... in run_server.sh, set BACKEND_API_KEY=... in run_server.bat). Pass the same key to connect(), or set it once as REDCEDAR_API_KEY:

import redcedar

client = redcedar.connect(api_key="<the BACKEND_API_KEY value from run_server.sh>")
print(client.status())   # {'ok': True, 'server_version': '0.93', 'sdk_version': '0.93.0'}

Without the key, status() and datasets.list() still work, but training, analysis, inference and explainable AI are refused (422, no key; 403, a wrong key). This key belongs to the server itself. A hosted server uses your personal API key instead (next section).

status() also tells you which versions you are using: the server's version (client.server_version gives it on its own) and the SDK's. The SDK's version follows the server's (SDK 0.93.x goes with server 0.93).

In REDCEDAR_URL, use 127.0.0.1 rather than localhost for a server on your own machine. On Windows, localhost is tried first as IPv6 (::1), which the server doesn't listen on, and every request then waits about 2 seconds.

A Hosted Server

Pass the URL of the hosted server and your API key:

client = redcedar.connect(url="https://<hosted-server-url>", api_key="your-api-key")

Or set environment variables once, and call redcedar.connect() with no arguments:

export REDCEDAR_URL="https://<hosted-server-url>"
export REDCEDAR_API_KEY="your-api-key"

Explicit arguments take priority over environment variables. A hosted server only accepts requests with a valid API key; without one, every call fails with 401 (no key or an unknown key) or 403 (a key without access).

Getting a key. Contact your Cascade Quantum representative to get an API key, or to get access to the Red Cedar user interface. If you already have access to the user interface, you can create your own key there, under API Keys. Keep the key private: it acts as you. You have one key at a time; a new key replaces the old one, which then stops working.

Local Mode, for Development

With the Red Cedar source and its dependencies in your Python environment, the SDK can call the Red Cedar code directly, with no server. Install the source once, from the red-cedar folder:

pip install -e .

Then connect in local mode:

client = redcedar.connect(local=True)

Every SDK call then runs the same function the server runs for it, in your own Python process and thread: no server, no port, no HTTP. Results are the same as through a server, and a debugger steps from the SDK call straight into the Red Cedar code. Without the install, pass the folder instead (connect(local="path/to/red-cedar"), or set REDCEDAR_CORE_PATH).

Local mode uses the datasets, trained models and job records of that red-cedar folder, the same ones a server started from it uses: a model trained through the server can be evaluated locally, and the other way round. Ctrl+C stops a local training run, as training.stop() does; the layers that finished are kept.

Data

Your Own Data

Red Cedar trains on tables: one row per example, input features first, and the last column is the target, the answer the model learns. A CSV file is the usual way to provide one.

  • Header row: optional. A first row counts as a header when it has text above a column of numbers. With a header, Red Cedar knows your columns by name, which inference.run() uses to match new files and explainable AI uses to name features. Without one, columns are known by position only.
  • One caveat: a file without a header whose last column holds text labels (such as M/B) has text in its first row and would be read as having a header. Give such files a header row.
  • Features are numbers. Red Cedar scales, normalizes and compresses them as part of training (see Data preparation under Settings).
  • Columns that are not features are left out by themselves, so you don't need to remove them first:
    • text columns, such as a patient name (a column of numbers with a few text values is still an error, to catch a data problem);
    • IDs: a column of whole numbers named like an ID (id, patient_id, sample, mrn, anything ending in _id, ...);
    • row numbers or sequential IDs at the start of the row, in a file without a header: whole numbers, all different, forming one unbroken run (such as 1 to 500), in a file of 20 rows or more.

Training reports the columns it left out (in the log, and when you upload a file in the web app), and they are never used for predictions either: new files may have them or not. A numbered ID with gaps in a file without a header can't be told from a measurement; give the file a header row naming it id.

Pass the path of a CSV file wherever a dataset is expected:

model = client.training.run("my_data.csv")

The file is uploaded each time. To upload once and reuse it, use datasets.upload(), which returns a dataset ID:

dataset_id = client.datasets.upload("my_data.csv")
model = client.training.run(dataset_id, settings={"num_qubits": 6})

Your Uploaded Files

Uploaded files stay on the server until you delete them. Each user sees only their own. List them, newest first, with datasets.uploads():

for f in client.datasets.uploads():
    print(f["id"], f["name"], f["rows"], f["task"], f["target"])

Each entry is a dict: id (the dataset ID), name, created_at, file_size, rows, columns, problem (why training can't use the file as it is, or None), and how training will use it: task (classification or regression), target (the target column's name, None without a header row) and classes; and models, the number of trained models that need the file.

Delete one with datasets.delete_upload(dataset_id). A model needs the file it was trained on: evaluation, predictions, training analysis and explainable AI read the training data again. When models isn't 0, delete those models first (inference.delete_model(), under Predictions), or keep the file while you use them.

client.datasets.delete_upload(dataset_id)

The Dataset Catalog

The server also has a catalog of ready-to-use datasets, such as "wdbc", "iris" and "diabetes".

for ds in client.datasets.list():
    print(ds["id"], ds["name"], ds.get("rows"), ds.get("classes"))

Each entry is a dict. The most useful fields: id, name, description, category, source, rows, columns, classes, available. The id is what you pass to the analysis and training calls.

Training

client.training.run(data, settings=None, verbose=False, on_progress=None, train_size=None, test_size=None, class_range=None, task=None)

Trains a model and waits until training ends.

Argument Type Default Description
data str required A CSV file path, a dataset ID from datasets.upload(), or a catalog ID
settings dict or str None Settings to change, as a dict or a .json / .toml file path (see Settings)
verbose bool or "log" False Print progress to stdout; "log" adds the server's log (Progress)
on_progress callable None Called with (percent, message) on each update
train_size float or int 0.8 Training set size, as a fraction or a number of rows
test_size float or int 0.2 Test set size, as a fraction or a number of rows; 0 trains on all rows
class_range list all classes Classes to train on, e.g. ["0", "1"] (catalog datasets only)
task str detected "classification" or "regression" (see Classification or Regression) 
model = client.training.run("my_data.csv", verbose=True, settings={
    "num_qubits": 6,
    "min_layers": 1,
    "max_layers": 2,
})

train_id = model["train_id"]

Returns a dict with train_id, task, train_samples, test_samples, total_layers, elapsed_seconds, data_loading_seconds, plus:

  • history: the training curves, by layer. Each layer has a list of {iteration, train_loss, train_accuracy} (no train_accuracy for regression).
  • validation: the test results at the end of each layer, by layer: test_loss, test_accuracy, test_accuracy_per_class, test_loss_per_class, num_parameters and timings. Regression has test_loss only. With test_size=0 the test values are None.
import matplotlib.pyplot as plt

for layer, points in model["history"].items():
    plt.plot([p["train_loss"] for p in points], label=f"layer {layer}")
plt.xlabel("Iteration"); plt.ylabel("Training loss"); plt.legend()

for layer, v in model["validation"].items():
    print(f"Layer {layer}: test accuracy {v['test_accuracy']:.1%}")

Training Loss and Accuracy

While a model trains, Red Cedar measures two numbers on the training rows after every parameter update, and returns them in history:

  • Training loss. For each row, the circuit gives a probability for every class. The row's loss is 1 minus the probability of its correct class: 0 when the model is certain of the right class, 1 when it gives that class no chance. The training loss is the average of these over the training rows, plus 10 times their variance. The variance term makes the optimizer prefer a model that does about equally well on every row over one that is very sure of some rows and wrong on others. Each parameter update is chosen to lower this loss.
  • Training accuracy. The share of training rows whose correct class gets the highest probability, that is, the rows the model classifies correctly.

The test loss and test accuracy in validation, and from training.evaluate(), are the same two measures on the rows held back from training. The training numbers are measured on rows the model learns from, so they usually look better than the test numbers; the test numbers tell you how the model will do on new data.

On a plot of the training curves, the loss usually falls quickly at first and then levels off. Once a layer's curve is flat, more parameter updates in that layer change little.

For a regression model, the loss measures how far the predicted number is from the target, as set by loss_type (default "weighted_hamming"), and there is no training accuracy.

Train and Test Rows

Every training run splits the data: by default 80% of the rows train the model and 20% are held back for testing. The split is stratified by class (each class keeps its share in both parts) and is the same every time for the same data. The held-out rows are what training tests at the end of each layer, and what training.evaluate() scores.

Holding rows back is what makes the test accuracy honest: accuracy measured on the training rows overstates how the model does on new data. The usual pattern when you want the final model to learn from everything:

  1. Train with the default split and check the test results.
  2. If they're good, train again with the same settings and test_size=0, and use that model for predictions.

With test_size=0 there is no held-out score: the test values in the layer results are None, and training.evaluate() and training.analyze() stop with an error saying the model has no test rows. To measure such a model, make predictions on rows that include the target column.

Layers

A model is trained one layer at a time, from min_layers to max_layers. Each layer adds a set of parameters to the circuit; by default (chain_layers=True) a layer starts from the parameters the layer before it found. Every finished layer is saved, and later calls take layer= to pick one (the highest by default).

Classification or Regression

The task is decided when the model is trained, and saved with it. Without task=, Red Cedar detects it from a CSV file's target column: text labels or whole numbers mean classification, numbers with fractions mean regression (catalog datasets are classification). A target of whole numbers that is really a quantity (a count, a score, a price in whole units) needs task="regression":

model = client.training.run("prices.csv", task="regression", settings={"num_qubits": 6})

task="classification" on a target with fractional numbers stops with an error, as does task="regression" on text labels.

A regression model predicts a number. The circuit encodes the target as a binary number on num_qubits_target qubits (default 2, taken from num_qubits); the prediction is the average of that number over the measured outcomes, scaled to the range of the training targets, so predictions stay between the smallest and largest target seen in training. Its test result is a loss (loss_type, default "weighted_hamming"); training.evaluate() and inference.run() also give the mean absolute error, in the target's units. Explainable AI works with classification models only.

client.training.status(train_id) and client.training.stop(train_id)

status() returns train_id, status (running, completed, failed or stopped), progress, summary and error_message. A job still waiting in the queue has no status yet (404).

stop() asks the server to stop a running training job; finished layers are kept. Since training.run() waits until the job ends, call stop() from another thread, notebook or process. The waiting training.run() then raises RuntimeError("Training stopped").

Evaluating a Model

Training already reports the test accuracy after each layer. The calls in this section look at a trained model again, later, in more detail.

client.training.evaluate(train_id, layer=None, settings=None, verbose=False, on_progress=None)

Scores a trained model on the rows held back from its training run. You pass no data: the server rebuilds the same split from the model's saved settings.

Argument Type Default Description
train_id str required The model, from training.run()
layer int highest layer Which layer of the model to score
settings dict None Execution settings only (backend, parallelize), e.g. to score on a different backend
verbose bool or "log" False Print progress to stdout; "log" adds the server's log (Progress)
on_progress callable None Called with (percent, message) on each update 
report = client.training.evaluate(train_id, verbose=True)

print(report["overall_accuracy"])
print(report["test_samples"])

for cls in report["per_class"]:
    print(f"Class {cls['class']}: {cls['accuracy']:.1%} ({cls['samples']} samples)")

Returns a dict with train_id, layer, task, overall_accuracy, overall_loss, test_samples, num_classes, per_class (a list of dicts with class, accuracy, loss, samples), and timings. For a regression model, overall_accuracy is None, per_class is empty, and mean_absolute_error gives the average error in the target's units. It reports on the held-out rows as a whole; for a result per row, use inference.run(). At most 400 held-out rows are scored.

client.training.analyze(train_id, layer=None, verbose=False, on_progress=None)

Replays the parameters saved during training on the held-out rows, giving the test accuracy and loss over the course of training. layer defaults to the highest layer.

replay = client.training.analyze(train_id)
plt.plot(replay["accuracy_history"])
plt.xlabel("Checkpoint"); plt.ylabel("Test accuracy")

Returns a dict with train_id, layer, num_checkpoints, accuracy_history, loss_history, final_accuracy, final_loss, and timings. Regression models have a loss history only.

Predictions

client.inference.run(train_id, data, layer=None, output=None, settings=None, verbose=False, on_progress=None)

Runs a trained model on new rows and returns one result per row.

Argument Type Default Description
train_id str required The model, from training.run()
data str required A CSV file path, or a dataset ID from datasets.upload()
layer int highest layer Which layer of the model to use
output str None Also write the results to this CSV file
settings dict None Execution settings only (backend, parallelize)
verbose bool or "log" False Print progress to stdout; "log" adds the server's log (Progress)
on_progress callable None Called with (percent, message) on each update 
predictions = client.inference.run(train_id, "new_data.csv", output="predictions.csv")

for row in predictions["predictions"][:5]:
    print(row["prediction"], row["probabilities"])

Returns a dict with train_id, layer, task, rows, timings, and predictions, a list with one entry per row, in the order of the file:

  • Classification: {"prediction": "M", "probabilities": {"M": 0.81, "B": 0.19}}. The labels are the ones in the training data.
  • Regression: {"prediction": 152.3}.

If the new rows also contain the target column, the result has an accuracy as well (regression: a mean_absolute_error). The output file holds the input columns plus a prediction column and, for classification, one probability_<class> column per class.

The new rows are prepared exactly as the training data was (scaling, compression, encoding), using the training data, which must therefore still be on the server.

Matching the Columns of a New File

The model has to pair each column of the new file with one of its inputs:

  • The file has a header row (a first row that is all text): columns are matched by name. They can be in any order. Columns the model doesn't use (an ID, say) are ignored. A missing feature column stops with an error naming it. If the target column is present (under its training name), the accuracy is reported too.
  • No header row: columns are matched by position. The columns must be the training features in training order, optionally followed by the target column. Any other number of columns stops with an error saying how many were expected.

A model trained on a file without a header knows its columns by position only, so its new files are matched by position too.

client.inference.models()

Lists your six most recently trained models. On a hosted server, these are the models trained with your API key or your sign-in to the web app; other users' models are not listed.

for m in client.inference.models()["models"]:
    print(m["train_id"], m.get("dataset_display_name"), m.get("num_qubits"), m.get("layers"))

Each entry includes train_id, dataset, dataset_display_name, num_qubits, layers (the completed layer numbers), max_layer, node_order, timestamp, non_defaults (the settings that differ from the defaults) and training_params.

Trained models are not kept forever: see Known Issues for how long a server keeps them.

client.inference.delete_model(train_id)

Deletes one of your trained models: its parameters and settings. A model that is still training can't be deleted; stop it first with training.stop().

client.inference.delete_model(model["train_id"])

Explainable AI

client.explainable.run(train_id, settings=None, verbose=False, on_progress=None)

Shows which input features drive the model's decisions. It uses the highest layer of the model. Each data qubit is mapped back to the input feature it encodes, and importance measures how much the feature influences the prediction: the probability that its qubit (or, for a feature on several qubits, any of them) reads 1.

What a data qubit encodes depends on the dimension_reduction setting. With "dimension_reduction": "none", each data qubit encodes one of your columns, and feature_name is that column's name. By default ("pca"), the columns are first combined into principal components, each a mix of all of them: feature_name is the component (PC1, PC2, ...), and made_of lists the columns with the largest shares of it, largest first, with the rest summed:

{"parts": [{"feature": "worst_perimeter", "share": 0.49}, {"feature": "worst_radius", "share": 0.23}, ...],
 "others": {"count": 26, "share": 0.13}}

The shares of all the columns add up to 1. A component with one or two large shares stands mostly for those columns; one with many small shares is a broad mix.

Argument Type Default Description
train_id str required The model, from training.run()
settings dict None Execution settings only (backend, parallelize)
verbose bool or "log" False Print progress to stdout; "log" adds the server's log (Progress)
on_progress callable None Called with (percent, message) on each update 
explanation = client.explainable.run(train_id, verbose=True)

for f in explanation["feature_importances"]:          # one per feature, most important first
    print(f"{f['feature_name']}: importance {f['importance']:.1%}")

for qid, val in explanation["convergence"].items():
    print(f"Class qubit {qid}: convergence = {val:.4f}")

Returns a dict with train_id, layer, dataset_name, num_qubits, num_class_qubits, class_range, qubit_map (a list of dicts with qubit, feature_index, feature_name, bits, bit, made_of, importance), feature_importances (below), convergence (class qubit ID to convergence value), distributions, feature_indices, and timings.

A feature can be encoded on more than one data qubit (with bits_type "2" or "3", or the default "importance", which gives the more informative features more qubits). qubit_map then has one importance per qubit, and feature_importances has one per feature, largest first: the probability that any of the feature's qubits reads 1. For a feature on one qubit that is the qubit's importance. Each entry has feature_name, feature_index, importance, qubits (each qubit with its own importance) and made_of. The same list, without qubits, is what a random forest returns.

for f in explanation["feature_importances"]:
    qubits = ", ".join(f"q{q['qubit']} {q['importance']:.0%}" for q in f["qubits"])
    print(f"{f['feature_name']}: {f['importance']:.1%} ({qubits})")

Random Forest

A random forest is a classical model: many decision trees, each trained on a random draw of the rows, that vote on each prediction. Red Cedar trains one as the baseline to compare the quantum model with. It is trained and used with the same calls as the quantum model; one setting chooses it:

forest = client.training.run("my_data.csv", settings={"model": "random_forest", "seed": 123})
print(f"Test accuracy: {forest['test_accuracy']:.1%}")

predictions = client.inference.run(forest["train_id"], "new_rows.csv")
importances = client.explainable.run(forest["train_id"])

Same rows as the quantum model. For the same file, train_size and test_size, the forest trains on the same rows as the quantum model and is tested on the same held-out rows (the split doesn't depend on the seed), so the two test results can be compared directly. Unlike the quantum model, the forest uses your columns as they are: no scaling, PCA, feature selection or bits. test_size=0 trains on every row, as for the quantum model.

Settings. The forest's own settings go in forest_options; the dataset, split, task and seed are the same settings as for the quantum model, and the quantum model's settings are ignored.

Setting Default Description
n_estimators 300 Number of trees, 1 to 2000. More trees give steadier results and take longer
min_samples_leaf 5 Fewest training rows at the end of a branch; larger keeps the trees simpler
max_depth None Most levels a tree may have (None: no limit)
max_features usual for the task Features each branch point chooses from: "sqrt" (the default for classification), "log2" or "all" (the default for regression)
class_weight None "balanced" gives rare classes more weight (classification only)
seed random Fixes which rows and features each tree draws, so a run can be repeated. Without one, the server picks a seed and saves it with the model 
settings = {"model": "random_forest", "seed": 7,
            "forest_options": {"n_estimators": 500, "min_samples_leaf": 3}}
forest = client.training.run("my_data.csv", settings=settings)

A value the forest can't use (for example 2001 trees, or an unknown setting) stops with a 400 error naming it.

Results. training.run() returns train_id, model ("random_forest"), task, train_samples, test_samples, num_features, fit_seconds, elapsed_seconds, train_accuracy (classification), and, when there is a test set, test_accuracy and per_class (classification) or mean_absolute_error and r2 (regression). history and validation are empty: a forest is fitted in one step, with no training curve or layers.

  • training.evaluate(train_id) scores the held-out rows: overall_accuracy and per_class, or mean_absolute_error and r2 for regression. The loss fields are None: a forest has no loss comparable with the quantum model's.
  • inference.run(train_id, data) returns the same fields as for the quantum model. A class's probability is the share of trees that voted for it.
  • explainable.run(train_id) returns feature_importances, a list of {feature_name, importance}, largest first. The importances add up to 1: each is the share of the trees' error reduction that comes from that column.
  • training.analyze(train_id) stops with an error: there is no training to replay.
  • layer= is ignored, and inference.models() shows "model": "random_forest" for a forest.

Running beside quantum jobs. A forest job doesn't wait for a quantum training to finish: the server runs one forest job and one quantum job at a time, side by side. Forest models count toward the same per-user model limit as quantum models.

Dataset Analysis

Three calls help you understand a dataset before training. All three take a catalog ID or a dataset ID from datasets.upload(), plus verbose and on_progress.

client.analysis.pca(dataset_id)

Principal Component Analysis: how many independent dimensions carry real signal in the data.

pca = client.analysis.pca("wdbc", verbose=True)
print(pca["features"])              # 30
print(pca["thresholds"]["90"])      # 7  (components for 90% of the variance)

Returns dataset_name, features, samples, n_components, variance_ratios, cumulative_variance, thresholds (percentage to number of components), and timings.

client.analysis.mi(dataset_id)

Mutual information. The data is first reduced with PCA, as training does, and each principal component (PC1, PC2, ...) is ranked by how strongly it predicts the target.

mi = client.analysis.mi("wdbc", verbose=True)
for f in mi["ranked_features"][:5]:
    print(f["feature_name"], f["mi_score"])

Returns dataset_name, samples, features, classes, total_mi, ranked_features (with rank, feature_index, feature_name, mi_score, mi_percent), cumulative_mi, thresholds, and timings.

client.analysis.qre(dataset_id)

Quantum resource estimation: how many qubits the model needs for this dataset. The data is encoded with more and more qubits until no two rows with different classes look the same (so 100% accuracy is possible in principle), plus the qubits needed for the class. The result is averaged over 10 random train/test splits.

qre = client.analysis.qre("wdbc", verbose=True)
print(qre["estimatedQubits"], "+/-", qre["standardDeviation"])

Returns dataset_name, estimatedQubits, standardDeviation, samples, features, classes, plotData (the highest possible train and test accuracy for each number of data qubits), warning_message, and timings.

Settings

The calls above work with no settings at all. Every part of a model can also be set: the circuit and its architecture, how the data is prepared, how training runs, and where the circuits execute.

Passing Settings

Settings are a Python dict, or the path of a .json or .toml file. Only the keys you give change; everything else keeps its default. Keys the server doesn't recognize are ignored without an error, so check the spelling against the tables below.

# Dict
client.training.run("my_data.csv", settings={"num_qubits": 8, "seed": 123})

# JSON file
client.training.run("my_data.csv", settings="my_settings.json")

# TOML file (Python 3.11+, or the tomli package)
client.training.run("my_data.csv", settings="my_settings.toml")

The same settings choose and configure a random forest: "model": "random_forest", and its own settings in forest_options. The quantum model's settings are ignored for a forest; seed, the train and test split and task apply to both. For example, a forest.json file:

{
  "model": "random_forest",
  "seed": 7,
  "forest_options": {"n_estimators": 500, "min_samples_leaf": 3}
}

client.training.run("my_data.csv", settings="forest.json")

Every trained model saves its full settings, so any run can be repeated, or used as the starting point for the next one.

training.run() takes all settings. training.evaluate(), inference.run() and explainable.run() use the model's own settings, fixed when it was trained; their settings= changes only how the circuits are run (backend, parallelize).

Circuit and Architecture

Key Default Description
num_qubits 4 Number of qubits in the circuit
min_layers 1 First layer in the layer sweep
max_layers 2 Last layer in the layer sweep
chain_layers True Start each layer from the parameters the layer before it found (False: each layer starts from scratch)
circuit_structure "bipartite" How the circuit's nodes are arranged
ansatz_type "euler_and_heisenberg" Gate ansatz of the parameterized circuit
activation_type "discretize" Activation function
node_order_type "sequential" Order in which the optimizer visits the nodes
op_direction "backward" Order of the ansatz operators over the data qubits ("backward" or "forward")

Key Default Description
normalize True Normalize features to the [0, 1] range

copula True Apply a copula transform to the training data

The split into training and test rows is set with the train_size, test_size and class_range arguments of training.run().

Running on Quantum Hardware

The backend setting chooses where circuits run. "statevector", the default, is an exact simulator. Other backends include "ionq-simulator", IonQ quantum computers, and IQM quantum computers ("iqm-garnet", "iqm-sirius", "iqm-emerald"). Which backends a server offers depends on how it is set up and which provider accounts it has.

Hardware time is expensive, and training runs many circuits. A common pattern is to train on a simulator, then evaluate the trained model, or make predictions, on hardware:

model = client.training.run("my_data.csv", settings={"num_qubits": 6})

report = client.training.evaluate(model["train_id"], settings={"backend": "iqm-garnet"})
print(report["overall_accuracy"])

On hardware, results are estimated from shots and carry noise, so they differ somewhat from the exact simulator.

Command Line

Installing the SDK also installs the redcedar command, for training and predictions without writing Python. It uses the same server connection (REDCEDAR_URL, REDCEDAR_API_KEY).

redcedar train my_data.csv --qubits 6 --layers 2 --seed 123
redcedar evaluate <train_id>
redcedar predict <train_id> new_data.csv -o predictions.csv
redcedar explain <train_id>
redcedar models
redcedar status
Command Same as Flags
redcedar train training.run(); prints the test results and the train_id --settings, --set, --model, --trees, --qubits, --layers, --min-layers, --nodes, --batch-size, --parallelize, --seed, --backend, --task, --test-size, --save
redcedar evaluate training.evaluate() --layer, --backend
redcedar predict inference.run(); prints the predictions, or writes them with -o --layer, --backend, -o
redcedar explain explainable.run(); prints the features the model relies on, most important first --top (default 10), --backend

Before the command, --url and --api-key choose the server, --local uses local mode (the Red Cedar code in this process, no server), -q turns off the progress output, and --log adds the server's log for the job. Run redcedar <command> --help for the details.

Settings on the Command Line

redcedar train takes settings from three places, each over the one before (and all over the server's defaults):

  1. --settings FILE: a .json or .toml file of settings, as in Passing Settings. It holds settings only, not the data, so one file can be used with any data file.
  2. --set KEY=VALUE, repeatable: any setting. Values are read as JSON when they can be (8, 0.5, true, null), otherwise as text. A dotted key sets a value inside a group: --set forest_options.n_estimators=500.
  3. The named flags:
Flag Setting
--model quantum or random_forest model (default: the quantum model)
--trees N forest_options.n_estimators (random forest)
--qubits N num_qubits
--layers N max_layers (from layer 1, unless --min-layers)
--min-layers N min_layers
--nodes N or all nodes optimized per layer: num_iterations, or all_nodes
--batch-size N batch_size (default: all training rows)
--parallelize parallelize
--seed N seed
--backend NAME backend
--task, --test-size as in training.run()

--save DIR also writes the result to DIR/<train_id>.json: the data file and the settings sent, the training curves and the test results per layer. The model itself is kept by the server with its full settings, for evaluate, predict and explain.

redcedar train my_data.csv --settings my_settings.toml --set num_pca=8 --nodes all --save results
redcedar train my_data.csv --model random_forest --trees 500 --set forest_options.min_samples_leaf=3
redcedar train prices.csv --task regression --qubits 6 --seed 7

Moving from run_qml_workflow.py

Developers who trained with run_qml_workflow.py (classification) or the regression workflow's runner, editing settings.py, can do the same with redcedar train, with or without a server (--local):

run_qml_workflow.py redcedar train
dataset_name in settings.py the data argument: a CSV file or a catalog ID
the other values in settings.py a settings file (--settings), and --set for single values
--num-qubits N / -n N --qubits N
--min-layers, --max-layers --min-layers, --layers
--num-iterations N --nodes N
--batch-size N / -bat N --batch-size N
--no-parallel the default; --parallelize turns it on
--backend --backend
the regression workflow --task regression
results under results/ the model is kept by the server; --save DIR writes the results to a folder

The command line's defaults are the server's (for example 4 qubits and all nodes per layer), which differ from those in the workflows' settings.py; put the values you rely on in your settings file.

If the redcedar command isn't found (pip's scripts folder isn't on your PATH, which is common on Windows and with conda), use python -m redcedar instead: python -m redcedar train my_data.csv.

Progress and Errors

Progress

All long-running calls take verbose and on_progress, which can be used together:

  • verbose=True prints a single updating line, such as [ 30%] Layer 1/2, and the test result after each layer of a training run. While the job is working, a dot is added to the line every few seconds (every 2 seconds at first, then every 5, then every 10 on a long step). While the job waits in the queue it prints Waiting in queue....
  • verbose="log" prints the same, plus the server's full log for the job (the training output of every iteration, timings, the model's structure). It's meant for finding out what went wrong.
  • on_progress is called with (percent, message) on each update, for your own progress bars or logging.
def my_callback(percent, message):
    log.info(f"{percent}% - {message}")

model = client.training.run("my_data.csv", verbose=True, on_progress=my_callback)

Errors

The SDK raises standard Python exceptions:

  • requests.ConnectionError: the server can't be reached. Use client.status() to check before starting work.
  • requests.HTTPError: the server returned an error, such as 404 for a training job that doesn't exist or 401 for a wrong API key.
  • RuntimeError: a job failed (the server's error message is included), or it was stopped with training.stop() ("Training stopped").
try:
    model = client.training.run("my_data.csv", verbose=True)
except RuntimeError as e:
    print(f"Training failed: {e}")

Limitations

Some things are not possible yet: explainable AI for regression models, your own data loaders and custom circuit components (only CSV files and the catalog, and the built-in components chosen by settings), stopping jobs other than training, and keeping models on a server indefinitely. The Known Issues page lists these and other known problems.
